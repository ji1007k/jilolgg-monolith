# 기능별 전담 에이전트 작성 가이드

이 프로젝트는 기능 영역별로 Claude Code 서브에이전트를 둔다. 매 세션이 도메인 맥락을 처음부터 다시 파악하는 비용을 줄이고, "이건 이렇게 하면 안 된다"는 암묵적 규칙을 문서로 고정하는 것이 목적이다.

**레퍼런스 구현**: [`.claude/agents/match-sync.md`](../.claude/agents/match-sync.md) — 새 에이전트를 만들 땐 이 파일을 열어놓고 같은 골격으로 쓴다.

## 위치와 파일명

```
jilolgg/.claude/agents/<name>.md
```

- git 추적 대상이다. 에이전트 문서의 값어치는 대부분 `파일:라인` 근거에 있고, 그건 코드가 바뀌면 같이 썩는다. 코드와 같은 커밋 히스토리에 있어야 리뷰 때 걸린다.
- **`.claude/agents/` 안에는 에이전트 정의가 아닌 `.md`를 두지 않는다.** 그 디렉터리의 모든 `.md`가 에이전트로 파싱된다. 이 가이드가 `docs/`에 있는 이유다.

### 로드 위치 — 루트에 junction이 걸려 있다

**확인된 사항**: Claude Code는 서브에이전트를 **세션 cwd의 `.claude/agents/`와 홈 디렉터리**에서만 찾는다. 하위 디렉터리는 탐색하지 않는다. 이 프로젝트의 세션 cwd는 래퍼 루트(`my-first-antigravity/`)이므로 `jilolgg/.claude/agents/`에만 두면 에이전트가 아예 로드되지 않는다.

그래서 래퍼 루트에 **디렉터리 junction**을 걸어뒀다.

```
my-first-antigravity/.claude/agents  ──(junction)──>  jilolgg/.claude/agents
```

파일 실체는 `jilolgg/` 한 곳뿐이다. 복사본도 동기화도 없고, 새 에이전트를 추가하면 자동으로 잡힌다. git이 보는 것도 `jilolgg/` 쪽 실체뿐이라 추적이 유지된다.

**에이전트 파일은 평소대로 `jilolgg/.claude/agents/`에서 수정하면 된다.** 아무것도 더 할 필요 없다.

junction이 없어졌을 때(저장소를 새로 클론했거나, 다른 OS에서 작업할 때) 다시 만드는 명령 — 관리자 권한은 필요 없다:

```bash
cmd //c mklink //J ".claude\agents" "jilolgg\.claude\agents"
```

PowerShell이면:

```
New-Item -ItemType Junction -Path .claude\agents -Target jilolgg\.claude\agents
```

기억할 것: **에이전트 목록은 세션 시작 시점에 확정된다.** 파일을 새로 넣거나 고쳐도 진행 중인 세션에는 반영되지 않는다. 새 세션을 열어야 한다.

## 명명 규칙

`<도메인>-<관심사>`. 소문자 kebab-case.

| 에이전트 | 상태 | 담당 |
|---|---|---|
| `match-sync` | 작성됨 | 동기화/배치 파이프라인 |
| `auth-security` | 후보 | JWT/CSRF/SecurityConfig/권한 이중 설정 |
| `match-manual-data` | 후보 | 수동 입력 경기, 외부 매핑, 오버라이드 |
| `lol-query` | 후보 | 조회 레이어 + 캐시(`MatchService`, `MatchCacheService`, dedupe) |
| `notification-fcm` | 후보 | FCM 푸시 |
| `frontend-web` | 후보 | `frontend/**`, Express 프록시, `/api` prefix |

## Frontmatter

```yaml
---
name: match-sync
description: >-
  (언제 이 에이전트에 위임할지를 트리거 문구로 쓴다)
model: inherit
---
```

- `name` — 파일명과 일치시킨다.
- `description` — **가장 중요한 필드다.** 에이전트 목록에는 `name`과 `description`만 노출되고 본문은 위임된 뒤에야 읽힌다. 즉 **위임 여부는 오직 이 필드로 결정된다.** 기능 나열이 아니라 **사용자가 실제로 할 법한 말**을 넣는다.
  - 나쁨: `Spring Batch 설정과 동기화 서비스를 관리합니다`
  - 좋음: `"배치가 안 돈다", "경기 데이터가 갱신되지 않는다", "파티션을 튜닝한다" 같은 요청에 사용한다`
  - 위임이 잘 안 걸리면 본문을 고치지 말고 **여기에 트리거 문구를 추가한다.**
- `model` — `inherit`가 기본. 메인 세션 모델을 따라간다.
- `tools` — **구현까지 하는 에이전트면 생략한다**(전체 도구 상속). 읽기 전용 조사 에이전트로 만들 때만 `Read, Grep, Glob, Bash`처럼 명시한다.

## 본문 8개 섹션

순서와 번호를 고정한다. 에이전트마다 섹션을 다르게 만들면 비교와 유지보수가 어려워진다.

### 1. 담당 범위

**담당과 비담당을 둘 다 적는다.** 비담당이 없으면 에이전트가 아무 데나 손댄다.

- 담당은 표로. 영역별 실제 경로를 적는다.
- 비담당엔 "경계에 닿으면 수정하지 말고 알리고 멈춘다"를 명시한다.
- **예외 규칙**을 별도로 적는다 — 비담당 영역이라도 담당 흐름에서 호출하는 지점은 담당인 경우가 많다.

### 2. 아키텍처 요약

이 영역의 흐름을 코드 없이 읽고 이해할 수 있게. 진입점 → 중간 계층 → 종착점 순서. ASCII 다이어그램과 표를 적극적으로 쓴다. 프로필별로 동작이 갈리면 표로 정리한다.

### 3. 불변 규칙

어기면 안 되는 것. 번호를 매기고, **각 규칙에 "왜"를 붙인다.** 이유 없는 금지는 지켜지지 않는다.

마지막에 "꼭 필요하다고 판단되면 먼저 사용자에게 근거를 제시하고 확인받는다"를 넣는다. 규칙을 절대 금지로 만들면 정당한 리팩터링까지 막힌다.

### 4. 알려진 함정

**이 섹션이 에이전트 문서의 핵심이다.** 나머지는 코드를 읽으면 알 수 있지만, 이건 아니다.

품질 기준:

- **코드에서 실제로 확인한 것만 적는다.** 추측은 적지 않거나 "확인 필요"로 명시한다.
- **모든 항목에 `파일:라인` 근거를 단다.**
- 제목 뒤에 `(확인됨)` / `(확인 필요)`를 붙여 신뢰도를 구분한다.
- 함정마다 "그래서 어떻게 하라"를 `→`로 덧붙인다.
- 파급이 큰 수정(엔티티 `equals`, 트랜잭션 경계 등)은 "사용자 확인을 받으라"고 명시한다.

### 5. 작업 절차

자주 오는 요청 유형별 순서. 요청 문구를 그대로 소제목으로 쓴다("경기 데이터가 갱신되지 않는다"). 진단 절차는 **범위를 좁히는 순서**로 — 어느 경로인지 먼저 특정하고, 그다음 계층별로 내려간다.

### 6. 검증

**복붙 가능한 실제 명령**을 적는다. 그리고 그 명령을 실제로 한 번 돌려보고 적는다.

주의사항에 반드시 포함할 것:

- 기존에 실패하는 테스트가 있으면 그 사실과 원인 — 없으면 에이전트가 자기가 깬 줄 안다
- 외부 의존(네트워크, 원격 Redis, 외부 API) — 실패 원인 구분을 요구한다
- 프로필/환경 전제

### 7. 보고 형식

변경 파일 / 근거(`파일:라인`) / 실행한 검증과 결과 / 확인 못 한 것. **"테스트가 실패했으면 실패했다고 그대로 적는다"를 명시한다.** 그 영역 고유의 필수 보고 항목(예: 캐시 무효화 정책 판단)이 있으면 추가한다.

### 8. 참고 문서

`docs/` 안의 관련 문서와 `jilolgg/CLAUDE.md`. 각 항목에 한 줄 설명을 단다.

## 전체 품질 기준

1. **담당과 비담당을 둘 다 적는다.**
2. **"알려진 함정"은 코드에서 확인한 것만, `파일:라인`과 함께.** 확신이 없으면 "확인 필요"로 표시하고 단정하지 말라고 지시한다.
3. **검증 명령은 실제로 돌려본 것만 적는다.**
4. **규칙엔 이유를 붙인다.**
5. **한국어로 쓴다.** 이 프로젝트의 주석·로그가 한국어다.
6. 새 에이전트를 만들면 이 문서의 표, `docs/README.md` 색인, 그리고 **최상위 래퍼의 `CLAUDE.md` 위임 목록**을 함께 갱신한다. 파일 자체는 junction 덕분에 따로 옮길 필요 없다.

## 위임 규칙은 어디에 쓰나

두 군데를 나눠 쓴다. 역할이 다르다.

| 위치 | 역할 | 성격 |
|---|---|---|
| 에이전트 파일의 `description` | 위임 판단의 **유일한 입력** | 힌트 — 상황에 따라 판단됨 |
| 최상위 래퍼 `CLAUDE.md`의 위임 목록 | "이 영역은 무조건 위임하라" | 규칙 — 판단에 맡기지 않음 |

**`jilolgg/CLAUDE.md`에는 라우팅 규칙을 쓰지 않는다.** 중첩 `CLAUDE.md`는 그 디렉터리 파일을 건드릴 때 로드되는데, 위임 결정은 그보다 먼저 일어난다. 규칙이 도착할 때쯤엔 이미 늦다. 최상위 래퍼 `CLAUDE.md`는 세션 cwd라 항상 첫 턴부터 로드된다.

단, 최상위 `CLAUDE.md`는 git 저장소 밖이라 버전 관리가 안 된다. 에이전트를 추가/삭제할 때 갱신을 빠뜨리기 쉬우니 위 6번 절차를 지킨다.

## 새 에이전트 만드는 순서

1. 담당 영역의 코드를 전부 읽는다. 진입점부터 종착점까지 흐름을 추적한다.
2. **읽으면서 이상한 점을 메모한다** — 이게 4번 섹션이 된다. 주석과 실제 동작이 어긋나는 곳, 두 경로가 같은 걸 다르게 처리하는 곳, 호출돼야 할 것 같은데 안 되는 곳.
3. 검증 명령을 실제로 돌려본다.
4. `match-sync.md`를 복사해 8개 섹션을 채운다.
5. 완성 후 그 에이전트에게 시험 과제를 던진다. 답에 `파일:라인` 근거가 붙어 오는지, 비담당 영역을 건드리지 않는지 확인한다.
